# Approach and trade-offs

I prioritised the core author-to-support workflow: authors can securely view their own catalogue and raise a query; support staff can triage the shared queue, inspect the author's context, generate and edit a suggested response, send it, and leave private notes. Status, category, and priority remain human-overridable. The seeded 10-author/18-book dataset is used on first run, including in-production titles, null values, and zero royalties.

The backend uses Express with clear middleware boundaries for authentication and role checks, Zod validation, and consistent JSON errors. MongoDB Atlas stores users, authors (with their books embedded), tickets, messages, internal notes, and ID counters in separate collections. The provided sample JSON is used only to seed an empty database. To keep this assignment implementation compact, the current persistence adapter loads records into memory and upserts the current state after mutations; it is designed for a single API instance, not concurrent multi-instance production traffic. A production evolution would use per-record repository operations, indexes, transactions/atomic updates where appropriate, and integration tests.

For AI, the server sends only the current query and relevant book context alongside a compact policy knowledge base. The prompt asks for constrained JSON classification, priority, and a professional response. The model is used only for a draft: an admin must review and explicitly send it. The OpenAI key stays server-side. Missing keys, rate limits, malformed responses, and provider errors fall back to deterministic rules and a policy-based template so intake and manual handling still work. This is cheaper and more resilient than sending the full conversation history and knowledge base on every call, though a production system should measure token usage, add retry/backoff for transient failures, and evaluate classification quality against labelled examples.

The UI polls every five seconds to satisfy near-real-time updates with less operational complexity than a socket server. For a larger deployment I would switch to SSE or WebSockets, use a durable queue for AI work, add audit history and SLA metrics, and instrument the service. The attachment control is intentionally UI-only, as allowed by the brief. Other next steps would include automated API tests, stronger account lifecycle flows, rate limiting, and a private deployment with managed secrets.
